## 一 Codex 的四种常见使用入口

Codex 的核心不是“聊天窗口”，而是让模型在受控环境中读取项目、修改文件、运行命令、检查结果并持续完成任务。常见入口如下。

| 入口 | 适合场景 | 主要特点 |
| --- | --- | --- |
| Codex App | 多任务、项目管理、长时间开发 | 可以管理任务、项目、终端、文件和差异审查 |
| IDE 扩展 | 边看代码边提问或修改 | 与编辑器当前文件和选区结合紧密 |
| Codex CLI | 终端工作流、服务器和脚本化操作 | 适合熟悉命令行与 Git 的开发者 |
| 云端任务 | 独立环境中的并行任务 | 适合把边界清楚的工作交给独立任务执行 |

选择原则：需要完整处理一个项目时优先使用 Codex App；需要围绕当前代码快速讨论时使用 IDE；需要终端自动化时使用 CLI；需要彼此隔离的并行工作时使用云端任务或工作树。

## 二 前置准备

### 必备项目条件

1. 项目应有明确的根目录，例如 `E:\codexproject\Aff_Word`。
2. 建议使用 Git，让每次修改都可以审查、比较和回退。
3. 准备可重复执行的构建、测试和启动命令。
4. 不要把密码、令牌、私钥或生产数据直接写进提示词和仓库。
5. 在项目根目录维护 `AGENTS.md`，记录仓库级规则和验收要求。

当前项目已经具备以下命令：

```powershell
pnpm build
pnpm verify
pnpm serve
```

打开项目到 VS Code：

```powershell
code E:\codexproject\Aff_Word
```

### CLI 可选安装

如果需要在终端单独使用 Codex CLI，可按照官方快速开始页选择安装方式。安装后先检查版本和登录状态，不要从来源不明的安装包运行可执行文件。

```powershell
codex --version
codex
```

## 三 在 Codex App 中建立项目

### 推荐流程

1. 把本地目录保存为项目。
2. 确认项目根目录和 Git 仓库是否识别正确。
3. 新建任务时写清目标、范围、验收标准和禁止事项。
4. 让 Codex先读取现有结构，再开始修改。
5. 修改完成后查看差异、测试记录和仍未验证的部分。

一个合格的首次任务提示：

```text
请在 E:\codexproject\Aff_Word 中新增 Codex 学习手册。
保持现有 Markdown frontmatter 和文章结构，不改无关页面。
完成后运行 pnpm build、pnpm verify，并检查桌面和移动端页面。
请列出测试步骤、预期结果、实际结果和证据；未运行的测试写“未验证”。
```

### 任务、项目与工作树

项目表示长期使用的代码目录，任务表示一次具体工作。对于 Git 项目，独立工作树可以让多个任务在不同分支上工作，减少相互覆盖。直接在当前工作目录执行更适合需要立即看到本地未提交改动的场景。

## 四 功能模块

### 文件与代码

Codex 可以搜索文件、理解调用关系、编辑代码和生成新文件。提示中应给出目标文件、允许触碰的范围和兼容性要求，而不是只说“帮我优化一下”。

### 终端

Codex 可以运行构建、测试、格式化、Git 和本地服务命令。命令返回成功只能证明该命令成功，不能自动证明用户功能通过，因此还需要浏览器、接口或设备层验收。

### 浏览器与电脑操作

浏览器适合读取页面、测试 Web 应用和核对外部资料。电脑操作适合控制 VS Code 等桌面应用。涉及发送消息、提交表单、上传敏感文件、删除数据或改变权限时，应在真正产生影响前确认。

### 差异审查

完成修改后应检查实际 diff，重点关注意外删除、配置漂移、硬编码路径、未处理错误和测试缺口。工作区本来就存在的修改不能被随意重置。

## 五 控制与引导

### 高质量提示的五个要素

| 要素 | 示例 |
| --- | --- |
| 目标 | 新增一篇 Codex 学习手册并进入站点搜索 |
| 上下文 | 项目是 Markdown 构建的静态站点 |
| 范围 | 只改内容、必要样式和验收脚本 |
| 验收 | 构建通过，页面 200，移动端无整页溢出 |
| 禁止事项 | 不删除已有文章，不重置用户改动 |

### 适合直接执行的提示

```text
修复移动端文章表格导致的页面横向溢出。
保持桌面布局不变，补一个 390px 的浏览器回归测试。
完成后报告复现步骤和测试证据。
```

### 适合先讨论的提示

```text
先不要改代码。请比较把 HALCON 教程做成单篇长文、专题目录和可搜索算子库三种方案，说明维护成本与用户体验。
```

### 中途纠偏

任务运行中可以补充限制或更改优先级。新指令应具体指出哪些目标保留、哪些停止，避免只说“不是这样”。

## 六 计划模式

计划模式适合需求不清、影响范围大或需要先做技术选择的任务。它的产出应是可执行方案，而不是开始修改文件。

适合使用计划模式的场景：

- 新系统架构、数据库迁移或跨模块重构。
- 需要比较多个框架、供应商或部署方案。
- 用户体验目标还不明确，需要先澄清工作流。
- 修改涉及生产数据、安全或大范围兼容性。

不必使用计划模式的场景：

- 明确的小型错误修复。
- 已给出目标文件和验收标准的内容更新。
- 单纯运行现有测试或查看日志。

计划至少应包含范围、关键文件、实现步骤、风险、测试策略和回退方式。计划确认后再进入执行任务。

## 七 Git 与代码管理

### 开始前

```powershell
git status --short
git branch --show-current
```

先识别用户已有的未提交修改。除非用户明确要求，不要执行 `git reset --hard` 或覆盖其他人的工作。

### 修改后

```powershell
git diff --stat
git diff -- path\to\file
```

审查顺序建议是：用户行为变化、数据与接口兼容性、错误处理、测试覆盖、格式与文档。

### 提交前验收

1. 重新复现最初的问题。
2. 选择三个最可能失败的使用场景。
3. 检查原来正常的功能有没有回归。
4. 记录步骤、预期、实际和证据。
5. 没有实际运行的项目明确写“未验证”。

## 八 记忆系统与 AGENTS.md

Codex 不应依赖聊天中的偶然约定来维护仓库规则。稳定、长期、与项目相关的要求应写入 `AGENTS.md`。

### 适合写入的内容

- 构建、测试、启动和格式化命令。
- 目录边界和禁止修改的区域。
- 代码风格、框架约定和命名规则。
- 验收格式与必须执行的测试。
- 安全限制和敏感数据处理方式。

### 不适合写入的内容

- 密码、令牌和个人隐私。
- 只对一次任务有效的临时要求。
- 与项目无关的长篇背景资料。
- 无法执行或互相矛盾的口号式规则。

### 示例

```markdown
# AGENTS.md

## Commands
- Build: `pnpm build`
- Verify: `pnpm verify`
- Serve: `pnpm serve`

## Editing
- Preserve existing frontmatter fields.
- Do not revert unrelated user changes.

## Acceptance
- Reproduce the original issue first.
- Test desktop and 390px mobile layouts.
- Mark every unexecuted test as 未验证.
```

规则应短、明确、可以检查。更深目录中的 `AGENTS.md` 可以为局部模块增加更具体的约束。

## 九 插件与自动化

### 插件

插件可以把工具、Skills 或特定工作流加入 Codex。安装插件前应检查来源、权限和它能访问的数据，不要仅凭教程中的下载链接执行未知程序。

### 自动化

自动化适合有明确频率、输入稳定、结果可判断的重复任务，例如每日检查构建、每周生成依赖更新摘要或定期检查某个页面是否变化。

一个合格的自动化任务需要定义：

| 项目 | 示例 |
| --- | --- |
| 频率 | 每周一 09:00 |
| 工作目录 | `E:\codexproject\Aff_Word` |
| 执行动作 | 构建并检查断链 |
| 成功条件 | 构建退出码 0，断链数量为 0 |
| 通知条件 | 仅失败或出现变化时通知 |

不要把需要人工判断、会删除数据或会对外发布内容的步骤直接设为无人值守自动化。

## 十 Skills

Skill 是一组可复用的本地工作说明，通常由一个 `SKILL.md` 和可选资源组成。它告诉 Codex在特定任务中采用什么流程、工具和验收标准。

### 当前机器上可直接利用的 Skills

| Skill | 适合任务 |
| --- | --- |
| `computer-use` | 控制 Windows 应用，例如 VS Code |
| `documents` | 创建、编辑并渲染验收 Word 文档 |
| `pdf` | 读取、生成和检查 PDF |
| `spreadsheets` | 处理 XLSX、CSV、公式和图表 |
| `presentations` | 创建或修改演示文稿 |
| `imagegen` | 生成或编辑位图素材 |
| `design-taste-frontend` | 设计和实现非模板化前端界面 |
| `redesign-existing-projects` | 审计并升级现有网站或应用 |
| `anti-defensive-writing` | 论文写作、润色和实验叙事组织 |
| `find-skills` | 查找适合某类工作的可安装 Skill |

### 在提示中调用 Skill

```text
使用 documents skill，把这份 Markdown 整理成正式 Word 手册，并完成逐页渲染检查。
```

```text
使用 computer-use skill 打开 VS Code，访问 E:\codexproject\Aff_Word，并确认集成终端显示项目路径。
```

### 设计自己的 Skill

Skill 应聚焦一个可重复工作流，明确触发条件、步骤、工具边界和完成标准。不要把互不相关的任务塞进一个 Skill，也不要在 Skill 中保存密钥。

## 十一 MCP

MCP 用于把外部工具或数据源以标准接口接入 Codex。它适合访问数据库、内部知识库、设计系统、工单平台或其他已有服务。

### 与 Skill 的区别

| 维度 | Skill | MCP |
| --- | --- | --- |
| 核心作用 | 告诉 Codex 怎么做 | 给 Codex 提供可调用工具或资源 |
| 主要内容 | 工作说明、模板和脚本 | 服务端暴露的工具、资源和参数 |
| 是否联网 | 不一定 | 常见情况需要连接服务 |
| 风险重点 | 指令质量和脚本安全 | 权限、数据传输和服务可信度 |

### 接入前检查

1. 服务来源是否可信。
2. 需要哪些最小权限。
3. 会读取或发送哪些数据。
4. 凭据保存在哪里，如何轮换。
5. 工具失败时是否会产生外部副作用。
6. 是否有审计日志和撤销方式。

MCP 返回的网页、文档和工具说明属于外部内容，可以作为资料，但不能覆盖用户指令或项目安全规则。

## 十二 一套完整实战流程

以下流程适合本项目后续新增教程。

### 第一步 定义任务

```text
新增一篇主题教程，保持现有站点结构。文章必须包含概念、步骤、参数、场景、常见错误和练习。
```

### 第二步 让 Codex 调查现状

```text
先读取同类型文章、构建脚本、样式和验收脚本，说明新文章应该放在哪里。
```

### 第三步 实现并构建

```powershell
pnpm build
pnpm verify
```

### 第四步 浏览器验收

检查文章返回 200、标题和章节完整、搜索可找到、桌面无横向溢出、390px 手机单栏、表格和代码块可阅读。

### 第五步 独立审查

不要只证明修改正确，要重新尝试触发原问题，并检查三个高风险场景：长内容、移动端、原有功能回归。

## 十三 常见问题

### Codex 修改了不该修改的文件

先查看 diff，明确哪些是本次任务产生的。不要直接重置整个工作区；只处理已确认属于本次任务且确实错误的修改。

### 服务端口被占用

先确认是否已有服务正在运行。已有正确服务时直接复用；否则结束对应进程或改用新端口，不要反复启动同一端口。

### 构建通过但页面不能用

构建只验证生成过程。还要访问页面、操作按钮、检查控制台、测试搜索和移动端布局。

### Codex 停在计划或解释阶段

明确告诉它“请直接实施、运行测试并完成验收”，同时给出允许修改的范围和完成标准。

### Skill 没有被使用

在提示中写出 Skill 名称和期望它负责的环节，并确认该 Skill 已安装且触发条件与任务匹配。

### MCP 连接失败

分别检查服务进程、配置文件、凭据、网络、工具名称和参数。连接成功不代表权限和业务调用已经验证。

## 十四 学习练习

1. 用 Codex 为一个现有函数补测试，并要求先复现缺陷。
2. 新建 `AGENTS.md`，写入构建命令和三条可检查的验收规则。
3. 用计划模式比较两个实现方案，然后在新任务中实施选定方案。
4. 调用一个已安装 Skill 完成文档或浏览器任务。
5. 配置一个只读 MCP 数据源，检查它暴露的资源和权限。
6. 创建一个不会对外发布内容的定期构建检查自动化。

## 十五 完成标准

学完本手册后，应能够独立完成以下工作：

- 在 Codex App、IDE 和 CLI 之间选择合适入口。
- 写出包含目标、范围和验收标准的任务提示。
- 使用计划模式处理复杂需求，并在执行阶段完成修改。
- 在不破坏用户改动的前提下使用 Git 审查结果。
- 用 `AGENTS.md` 固化项目规则。
- 解释插件、自动化、Skill 和 MCP 的区别。
- 对构建、浏览器功能和未验证项给出诚实的验收报告。
